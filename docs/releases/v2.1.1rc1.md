# Agent PBX 2.1.1rc1

Agent PBX 2.1.1rc1 is the TestPyPI rehearsal candidate for the first v2.1
maintenance release. It validates the new secretless release path while
carrying the runtime-recovery, managed-tmux, Codex-theme, and Joplin E2EE
repairs completed after 2.1.0.

This candidate is intended for release-pipeline qualification. Production
users should continue to use the latest stable release until the same reviewed
changes are published as 2.1.1.

## Managed Codex runtime recovery

- Explicit restart creates a fresh v2 managed tmux mapping when an Agent or
  Operator has no usable mapping, resumes the preserved Codex session, and
  verifies the replacement before recording it.
- Runtime commands use each mapping's exact tmux executable, socket, session,
  window, and pane. This prevents the host tmux 3.2 server from being confused
  with PBX-managed tmux 3.7 sessions.
- Follow-up delivery, scrollback, rollout lookup, resize, copy mode, and
  shutdown all follow the recorded runtime identity.
- Codex shutdown uses the supported `/quit` command and recognizes a stopped
  Codex process even when the tmux pane returns to its shell.

## Terminal color and syntax themes

- Agent PBX installs and selects the generated `agent-pbx-1337` Codex syntax
  theme through a drift-safe command and reports its state through doctor.
- Dedicated tmux runtime reconciliation removes stale inherited `NO_COLOR`
  state while preserving an explicit user request to suppress color.
- The original `cyberpunk` RGB palette is restored. The
  `cyberpunk-accessible` theme remains a distinct deuteranopia-friendly
  deep-teal alternative, including under an outer tmux 3.2 workspace.

## Joplin E2EE and response capture

- Same-profile Data API and CLI sync operations are serialized under an
  explicit profile-ownership policy.
- Encrypted notes render as locked rather than empty, and Agent PBX blocks
  mutation until decryption succeeds.
- Managed sync restores the exact validated Joplin Data API process without
  exposing E2EE credentials or ciphertext.
- Targeted response writes validate note identity and retain Codex session,
  transcript, turn-phase, line, mtime, and response-hash provenance.
- The TUI preserves note selection, reading state, and dirty drafts while the
  managed sync path restarts and verifies the Data API.

## Trusted Publishing rehearsal

The release candidate exercises the complete TestPyPI path:

- an immutable annotated prerelease tag identifies the package;
- the release validator matches tag, commit, version, changelog, release note,
  archive metadata, and target-index state;
- Linux and macOS test lanes run before publication;
- one isolated job builds the wheel and source distribution once;
- GitHub obtains a short-lived TestPyPI token through OpenID Connect;
- TestPyPI receives package attestations;
- post-publish verification compares the public files to the exact local
  artifact hashes and installs 2.1.1rc1 in a clean environment.

No PyPI API token or publishing password is stored in GitHub. The production
PyPI workflow remains gated by a separate publisher identity, environment,
stable tag, and published GitHub Release.

## Validation

This candidate is accepted only after the full local suite, release metadata
tests, archive inspection, wheel smoke installation, hosted Linux/macOS
matrix, TestPyPI Trusted Publishing deployment, public hash comparison, and
clean TestPyPI installation all pass.

# Agent PBX 2.3.0rc5

Agent PBX 2.3.0rc5 is the final release candidate for the v2.3 control-plane,
Operator-workflow, WorkerBee-policy, and runtime-resilience cycle. It retains
the activated RC4 product tree and repairs one isolated public-demo startup
edge case found by the first stable branch matrix: bearer tokens beginning
with `-` are now passed as one `--token=<value>` argument so `argparse` cannot
mistake the value for another option. No stable tag, GitHub Release, or PyPI
artifact was created from the failed stable gate.

The release keeps the v2 architectural boundary explicit:

- Agent PBX owns durable Agent and Operator identity, topology, policy,
  approvals, campaigns, handoffs, lifecycle, runtime mappings, and audit;
- Codex owns reasoning, tools, execution, and bounded subagents inside one
  root session;
- tmux owns persistent PTYs, panes, clients, geometry, and scrollback; and
- WorkerBee remains an optional runtime-truth, simulation, deployment, and
  validation plane.

## Operator authority and workflow

- Durable, source-addressed handoff completion receipts return terminal work
  to the exact root Operator or source fork and require explicit review
  acknowledgement.
- The TUI separates Operator workflow `State` and `Flow` from tmux `Live`
  state, exposes completion receipts through F8, and refuses report-mode
  delivery when no exact pane evidence exists.
- Versioned execution authority and exact Git workspace sets distinguish the
  public `scoped-edit` default, immutable `review-readonly`, explicit Trusted
  Workbench, and ceiling-gated local `full-access` profiles.
- Bounded delegation leases allow reviewed local workflows without turning an
  Operator role into ambient execution authority.
- Campaign assignments accept only reporter- and scope-bound terminal reports;
  terminal state is immutable and complete campaigns close deterministically.

## Exact Git checkpoints

Dedicated trusted workstations may enable an optional root-supervised Git
checkpoint workflow. A root Operator can request one exact checkpoint for its
own qualified Trusted Workbench edit fork and existing handoff. The local TUI
revalidates campaign, workspace-set, authority, parent, path, and subject
digests before performing a guarded stop, exact broker commit, and same-session
resume.

The broker is deliberately narrow. It:

- is local-TUI-only and is not exposed through the public API, MCP, or shell;
- observes and stages only reviewed leaf paths;
- binds raw bytes, modes, blob identities, prior index state, parent-chain
  identity, branch, HEAD, tree, ordered parents, index, ref, and reflog;
- rejects ambient merge, rebase, cherry-pick, revert, bisect, sequencer,
  sparse, split-index, promisor, alternate-object, and include-bearing states;
- journals a closed crash-recovery state machine; and
- never deletes shared Git objects during rollback.

Public installations remain in guided mode. Review forks cannot invoke,
approve, cancel, or impersonate this root workflow.

## Runtime identity and native terminal resilience

Managed lifecycle actions now require the complete tmux executable, socket,
server, session, window, pane, process-start, and Codex-session identity. A
same-number pane on the outer or another tmux server can never become a
fallback target.

Native Latest attachment and runtime-header results are selection-generation
aware. Agent/Operator changes, F4, and Joplin-to-Latest transitions preserve
the last valid native frame or a bounded loading surface, reject stale A→B→A
results, and enter the retained capture path only after a genuine attach
failure. Missing inactive runtimes can be reconciled only after fresh exact
server and process evidence proves that no target-owned pane or writer lease
exists.

## WorkerBee policy

Agent PBX 2.3 keeps four runtime-authority axes independent:

1. backend: OSS, platform-debug, or a future managed user appliance;
2. source mode: `native-direct`, `snapshot-import`, `trusted-direct-bind`, or
   `managed-clone`;
3. access profile: `observe-local`, `review-readonly`, `local-deploy`, or
   `trusted-workbench`; and
4. execution lane: the ordinary generation-bound gateway or a separately
   authorized immutable controlled run.

Workspace mobility and snapshot-content policy remain independent constraints.
Changing one axis never silently changes another. The committed public posture
remains conservative and approval-gated; review forks remain read-only.
Trusted direct bind requires the fixed helper, private receipt store, approved
roots, runtime prefix, and administrator ceiling together, and otherwise fails
closed.

## Joplin and long-running control-plane behavior

- Targeted Joplin write/readback health remains independent from strict
  whole-profile E2EE validation, so an unrelated historical encrypted item
  cannot falsify a verified new note write.
- Repeated targeted retries reuse the one active job rather than creating
  duplicate note or sync work.
- Long broker receipts remain inside bounded scrolling content while the
  receipt-bound confirmation controls stay visible.
- Existing paint throttling, frame coalescing, bounded terminal history,
  request coalescing, event-loop telemetry, keepalive limits, and daemon-log
  rotation remain in place.

## Compatibility and migration

Agent PBX 2.3.0rc5 advances the additive database contract from schema 30 to
schema 40. Qualification proves dry-run, apply, verification, and rollback
against a schema-30 fixture while preserving starred Agents, root Operators,
forks, events, campaigns, Codex session evidence, and tmux mappings.

Before upgrading a long-lived control plane:

```bash
agent-pbx doctor
agent-pbx migrate dry-run
agent-pbx migrate backup --retention-days 7
agent-pbx mcp stop
agent-pbx migrate apply --retention-days 7
agent-pbx migrate verify
agent-pbx mcp start
agent-pbx doctor
```

Running Codex processes do not need to restart solely for this Agent PBX
upgrade. Restart connected TUI clients so they load the new code, but leave the
managed tmux server and healthy Codex panes running.

Compatibility polling, the Thread tab, HTTP refresh, and captured terminal
paths remain available. Their future removal still requires measured parity, a
tested migration path, and published notice in a later release.

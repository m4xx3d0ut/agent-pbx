# Agent PBX 2.5.0rc1

Agent PBX 2.5.0rc1 is the first release candidate for the post-v2.4 component
and terminal-delivery cycle. It retains the v2.4 durable engineering control
plane while introducing behavior-preserving ownership boundaries, independently
governed WorkerBee Operator profiles, and exact readiness-bound terminal
delivery.

This candidate does not advance the database schema. Schema 45 remains the
current and required schema, so an existing v2.4 schema-45 database needs no
data migration.

## Component decomposition

The API, Textual TUI, and persistence layers now have explicit typed owners:

- FastAPI route families are registered through typed services while preserving
  every public path, method, request and response model, status code,
  authorization dependency, feature gate, and controller/executor boundary;
- Textual screens and controllers own presentation and orchestration without
  acquiring API, persistence, runtime, or authorization responsibilities; and
- persistence repositories own cohesive SQLite mechanics behind the compatible
  `Store` facade without changing schema, migrations, transaction boundaries,
  or public Store signatures.

Executable architecture guards pin import direction, component growth,
OpenAPI, route inventory, TUI composition, Store declarations, the schema-45
fingerprint, and the reviewed atomic-transaction inventory. The decomposition
does not itself grant a new operation or authority.

## WorkerBee Operator profiles and path evidence

WorkerBee access is independent from Codex, filesystem, Git, broker, provider,
deployment, publication, and credential authority.

- The committed Operator default remains `local-deploy`.
- Caller Agents remain `local-deploy` unless separately governed by an
  existing caller policy.
- Review forks are always forced to `review-readonly`.
- A root Operator or edit fork may use `trusted-workbench` only when the
  daemon-resolved WorkerBee ceiling and exact workspace-policy evidence permit
  it.
- Explicit durable entity intent takes precedence, while stale, missing,
  incompatible, or above-ceiling intent fails closed instead of being silently
  rewritten.

Versioned path-domain receipts distinguish the canonical host source root,
approved host-root ceiling, container target, and runtime workspace. They bind
the immutable WorkerBee binding, lease, backend generation, and policy digest.
Stale entity bindings, generation drift, and path-policy drift are rejected.

These controls do not stage, commit, or publish Git content. Exact broker
approval, workspace qualification, path receipts, and commit authority remain
separate.

## Typed terminal delivery

Report-mode delivery now proves the exact durable target through the complete
delivery operation:

- entity and Codex session;
- managed tmux server, socket, session, window, and pane;
- registered process PID and start ticks;
- workspace, workspace-set, and authority identity;
- runtime readiness and an idle input composer; and
- an exact writer lease held only for the bounded injection.

The service returns one explicit outcome: `delivered`, `queued`,
`target_not_ready`, `overlay_active`, `ambiguous`, `blocked`, or
`stale_mapping`. Queue fallback is available only to explicit nohup targets;
report-mode and tmux targets never silently queue or report success.

Caller-stable request IDs provide duplicate suppression, restart/replay safety,
and metadata-only audit evidence. Prompt bodies and secrets are not persisted
in delivery audit records.

Codex startup, model-selection or announcement, update, and thinking
interstitials are classified as `overlay_active`. Managed launch, restart, and
resume paths continue to set `check_for_update_on_startup=false`. Approval,
safety, credential, and destructive-confirmation prompts remain blocked and are
never suppressed.

## Release and recovery hardening

The release workflow includes an exact-tag recovery path for verifying an
already-published PyPI release and restoring its original prebuilt GitHub
Release assets without package-index publication authority. Package-index
verification tolerates bounded metadata-to-Simple-API propagation while still
requiring exact hashes and a clean installation.

TUI launches also retain private, bounded, redacted crash evidence without
changing ownership of managed tmux or Codex processes.

## Compatibility and defaults

| Contract | v2.5.0rc1 posture |
| --- | --- |
| Python | `>=3.10`, unchanged |
| Database | schema 45, unchanged from v2.4 |
| Public API and OpenAPI | compatibility-guarded; additive behavior only |
| Store and transactions | compatible facade and reviewed atomic inventory |
| WorkerBee public default | `local-deploy` |
| Review-fork WorkerBee profile | forced `review-readonly` |
| Trusted Workbench | explicit daemon ceiling plus workspace-policy evidence |
| Git broker and commit authority | independent and unchanged |
| High-authority engineering gates | default-disabled or explicitly manual |
| Stable v2.5.0 promotion | held pending RC qualification and review |

The release does not require a new workspace root, provider, credential,
deployment, publication, or runtime-mapping grant.

## Upgrade and rollback

Before upgrading a long-lived installation, create the normal database and
configuration backup and run the migration dry-run. The expected result from a
v2.4 schema-45 installation is `changes_required=false`:

```bash
agent-pbx doctor
agent-pbx migrate dry-run
agent-pbx migrate backup --retention-days 7
```

Load the candidate through the separately reviewed activation procedure. Do
not restart the managed tmux server or healthy Codex processes solely for this
upgrade. Verify daemon/package identity, schema 45, feature-gate defaults,
workspace roots, WorkerBee posture, and retained runtime mappings after the
daemon and TUI load the candidate.

Rollback stops only the Agent PBX daemon, restores the reviewed pre-upgrade
package/configuration identity and database backup if one was changed, and
starts the prior version. Managed tmux sessions and Codex processes remain
untouched.

## Qualification posture

RC qualification requires the complete bounded nonserial and serial suites,
component/OpenAPI/Store/schema/transaction guards, documentation and static
checks, distribution inspection, clean-wheel installation, offline wheelhouse
verification, and a disposable loopback-only harness. Host-only AF_UNIX, tmux,
Neovim, ptrace, and strace restrictions must be classified rather than hidden
by product changes.

The release candidate must then pass the immutable GitHub Linux/macOS and
Python 3.10/3.12 matrix, TestPyPI Trusted Publishing, registry hash validation,
and exact clean installation before any stable-promotion decision.

## Install the candidate

After TestPyPI qualification:

```bash
python -m pip install --index-url https://test.pypi.org/simple/ \
  --extra-index-url https://pypi.org/simple/ \
  agent-pbx==2.5.0rc1
```

This assignment stops at the stable-promotion decision boundary. It does not
create or publish stable v2.5.0.

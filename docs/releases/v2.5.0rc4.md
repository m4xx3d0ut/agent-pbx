# Agent PBX 2.5.0rc4

Agent PBX 2.5.0rc4 reconciles durable PBX workflow state with the live managed
runtime boundary. It addresses the remaining RC3 gaps around caller identities
without runtimes, direct Operator-to-caller campaigns, terminal campaign
closure, explainable `State`/`Flow`/`Camp` projection, and Codex MCP tool
inventory freshness.

The candidate advances the additive SQLite contract from schema 45 to schema
46. Existing Agents, Operators, forks, stars, reports, campaigns, handoffs,
Codex sessions, tmux runtime mappings, writer leases, and project ownership are
preserved. Existing campaign assignments migrate to the unchanged
`operator_fork` topology.

## Existing caller rehydration

An existing caller with durable PBX history but no managed runtime can now be
reintroduced through a preview/apply transaction. The safe initial mode:

1. validates the caller, persisted project root, model profile, WorkerBee
   profile, runtime server, and absence of a current runtime mapping;
2. records historical Codex session ownership as warning evidence;
3. binds apply to a deterministic preview token;
4. creates a fresh independent Codex session in a new managed tmux runtime;
5. atomically updates the existing caller and runtime mapping; and
6. removes only the disposable new tmux session if persistence fails.

The operation preserves the caller's PBX identity, project, stars, reports,
campaign references, and metadata not owned by the new runtime. It clears stale
session identifiers rather than silently resuming a historical session that may
belong to another PBX identity. `fork_source` remains fail-closed until the
installed Codex fork behavior is observed and qualified.

## Explicit campaign delivery topology

Campaign assignments now persist one of two topologies:

- `operator_fork`, the compatible default, creates or reuses the bounded
  Operator-fork workflow; or
- `direct_caller`, a root-Operator-only path that targets an existing caller
  through the normal exact terminal-delivery contract without creating a fork.

Follow-ups inherit the assignment topology and cannot switch it. A
`direct_caller` assignment cannot smuggle a fork identifier, and non-root
Operators cannot select the topology.

## Terminal campaign reconciliation

After campaign dispatch and follow-up processing, Agent PBX now reconciles the
campaign against all assignment states. When every assignment is terminal, the
campaign closes instead of remaining indefinitely `running`. Completion
receipts, approvals, failed delivery, and other durable review work remain
independent evidence and continue to win in the Operator projection until they
are explicitly resolved.

## Explainable Operator workflow projection

The Agent and Operator list projection now carries the primary and secondary
workflow sources, subject IDs, evidence timestamps, precedence reason, and
whether a report was superseded. The TUI detail view exposes those fields.

A newer active campaign may supersede an older terminal report when that report
is unscoped or belongs to a different campaign. The report is retained; only
the current presentation precedence changes. Blocked, approval, review,
completion, and other durable actionable evidence remains visible in `Flow`.

## MCP tool inventory freshness

At daemon construction, Agent PBX builds a canonical manifest from every
exposed FastMCP tool name, description, input schema, and output schema. The
manifest digest is published through authenticated diagnostics and stamped into
new managed/TUI Codex launch environments, entity metadata, and runtime mapping
evidence.

The resulting projection is deliberately conservative:

- `current`: the launched session digest matches the current daemon manifest;
- `stale`: both digests are known and differ, so a restart is required to load
  the new inventory;
- `unknown`: a live pre-RC4 runtime lacks launch provenance, so restart is
  recommended but mismatch is not claimed;
- `no_runtime`: the durable entity has no managed runtime; and
- `unavailable`: the daemon has no authoritative manifest evidence.

This is observability, not authority. Agent PBX does not grant tools, restart a
session, rewrite a mapping, or infer a legacy mismatch from the manifest alone.

## Compatibility and security

RC4 preserves the RC3 host-liveness watchdog, child-agent availability and
correlation, exact terminal-delivery evidence, WorkerBee access policy, Git
broker boundaries, provider and credential policy, review-fork restrictions,
and remote-client permissions.

The new paths retain these fail-closed boundaries:

- rehydration refuses existing mappings, duplicate managed sessions, stale
  previews, invalid roots, elevated/migration-only profiles, and unobserved
  source-session forking;
- direct delivery remains exact-target-only and uses the existing managed
  runtime, process, workspace, input-readiness, overlay, and writer-lease
  checks; and
- MCP inventory evidence cannot expand a session's tool, filesystem, network,
  WorkerBee, Git, provider, publication, or credential authority.

No prompt body, terminal transcript, hidden reasoning, secret, or provider
credential is added to the new records.

## Qualification boundary

Focused qualification uses isolated SQLite stores, mocked tmux servers,
disposable Textual applications, and generated compatibility fixtures. It
covers rehydration atomicity and rollback, topology enforcement, terminal
campaign closure, workflow precedence, manifest determinism, launch provenance,
TUI diagnostics, OpenAPI, schema, route inventory, and component boundaries.

The bounded local release runner completed on the candidate source with:

- **2,027 passed** and **2 expected opt-in skips** in the four-worker
  parallel-safe lane; and
- **3 passed**, **1 expected opt-in skip**, and **2,029 deselected** in the
  isolated serial lane.

The first full run correctly caught three stale test-contract literals that
still named schema 45 and the prior 33-operation atomic manifest. After those
explicit expectations were advanced to schema 46 and 35 operations, all 30
affected persistence, migration, and controlled-run tests passed serially and
the complete gate passed as reported above. No functional runtime, workflow,
TUI, or MCP test failed.

No live managed pane, Codex process, tmux server, runtime mapping, writer lease,
daemon, or TUI is used by automated qualification.

## Upgrade, activation, and rollback

Before activation, run the normal reviewed sequence:

```bash
agent-pbx doctor
agent-pbx migrate dry-run
agent-pbx migrate backup --retention-days 7
```

Activation is intentionally separate from installation. Existing running
sessions without manifest provenance appear as `unknown` and may be restarted
one at a time at a safe turn boundary; they are not restarted automatically.

The immediate source rollback parent is `e786fd4` plus the independently
reviewable RC4 checkpoint commits. Restoring the pre-RC4 database backup returns
the schema-45 representation if a full rollback is required. Rolling code back
without restoring the database remains supported because schema 46 is additive
and existing topology values use the prior behavior.

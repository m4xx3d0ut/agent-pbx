# Agent PBX 2.3.0rc3

Agent PBX 2.3.0rc3 is the final release candidate for the v2.3 control-plane,
Operator-workflow, WorkerBee-policy, and runtime-resilience cycle. It carries
the complete RC2 architecture onto the public GitHub and TestPyPI release path,
adds the final exact managed-stop repair, and aligns the migration contract with
the current schema 40 database.

Production users should continue to use Agent PBX 2.2.0 until this candidate
passes reviewed workstation activation and is promoted as 2.3.0.

## Release boundary

The v2.3 line preserves the established control-plane split:

- Agent PBX owns durable Agent and Operator identity, workspace ownership,
  policy, routing, approvals, lifecycle, campaigns, handoffs, and audit.
- Codex owns reasoning and execution inside each managed session.
- tmux owns durable PTYs, panes, sessions, geometry, attachment, and scrollback.
- WorkerBee remains an optional runtime-truth and bounded execution plane.

The public defaults remain conservative. Trusted Workbench authority,
root-supervised Git checkpoints, controlled WorkerBee runs, and trusted direct
binding require explicit local policy and never activate during package
installation or schema migration.

## Operator authority and workflow receipts

Agent PBX now separates Operator role from execution authority. Public
`scoped-edit`, immutable `review-readonly`, explicit `trusted-workbench`, and
administrator-ceiling `full-access` profiles use versioned exact workspace
sets, linked-worktree qualification, edit-fork inheritance, bounded WorkerBee
access, and restart/resume activation.

Operator handoffs produce idempotent completion receipts addressed to the exact
source root or source fork. Receipt delivery remains independent from the
authoritative handoff result, and the source Operator explicitly acknowledges
each reviewed result. The TUI exposes those receipts through F8 and separates
workflow `State` and `Flow` from tmux `Live` state.

Dedicated trusted workstations may enable a root-supervised exact Git
checkpoint workflow. The root Operator requests a checkpoint only for its own
activated Trusted Workbench edit fork and an existing exact-broker handoff. The
local TUI revalidates immutable campaign, authority, workspace, parent, tree,
and path evidence before guarded stop, exact commit, same-session resume, and
durable receipt delivery. Public installs remain in guided mode.

## Linked-worktree Git safety

Linked worktrees retain qualified common Git directories as explicit Trusted
Workbench launch roots even when a more-specific read-only mount would
otherwise override a writable parent. Narrow per-worktree, object, ref, and
reflog paths remain qualification evidence rather than additional Codex
workspaces.

Split secret/read/deny profiles continue to use the local stopped-fork broker
instead of weakening their deny rules. The broker observes only explicitly
reviewed leaves, starts from an empty staged set, binds raw-byte file and Git
identity, rejects unsafe repository state, journals a closed recovery machine,
and exposes no remote API, MCP, shell, implicit-stage, or arbitrary-message
surface. Ordered one-parent and two-parent checkpoints preserve the reviewed
tree and parent order.

## Managed tmux lifecycle

Stop, purge, restart, and resume operations bind the complete managed tmux
identity: executable, socket, server, session, window, pane, pane process, and
process-start evidence. A matching pane number on another tmux server can never
serve as fallback evidence.

The final RC3 repair permits one prepared stop transaction to finalize after
its exact frozen pane process is conclusively absent even when a distinct
replacement candidate is visible. The candidate is retained as audit metadata;
the original transaction never adopts, stops, rewrites, or deletes it.

Inactive missing-runtime reconciliation remains fail closed. It requires fresh
daemon evidence, matching server and socket provenance, no writer lease,
conclusive process absence, and no target-owned pane before clearing only the
stale local mapping.

## Native terminal and Joplin stabilization

Native Latest attachment, capture, and runtime-header results carry the current
selection generation. Joplin-to-Latest, F4, and Agent/Operator switches retain
the last valid frame or a bounded loading surface, reject stale A-to-B-to-A
results, and enter the compatibility view only after a genuine attach failure.

Targeted Joplin note-write health remains independent from strict whole-profile
E2EE validation. A verified new note remains successful when unrelated
historical notes are locked. Retry is Agent- and target-scoped, reuses an
existing queued or running job, survives store reopen, and renders locally
completed copies without waiting for a full profile probe.

## WorkerBee runtime policy

The WorkerBee integration keeps four runtime-authority axes independent:

1. backend selection;
2. source mode;
3. access profile;
4. execution lane.

Source modes are `native-direct`, `snapshot-import`, `trusted-direct-bind`, and
`managed-clone`. Access profiles are `observe-local`, `review-readonly`,
`local-deploy`, and `trusted-workbench`. The ordinary generation-bound gateway
remains separate from the root-owned immutable controlled-run lane.

Fresh public policy remains snapshot import with local deployment through the
ordinary gateway. Review forks remain read-only. Trusted direct binding is
platform-debug-only, requires an administrator ceiling, approved canonical
roots, safe ownership and ancestry, a host-owned helper receipt, runtime
revalidation, and zero-residue cleanup. Unknown advertised WorkerBee tools are
quarantined and denied until reviewed.

## Database migration

Agent PBX 2.3.0rc3 uses schema 40. Migration from the 2.2 stable schema 30 is
additive and introduces durable records for:

- Operator authority and workspace-set versions;
- Operator delegation leases;
- action transactions and receipts;
- handoff completion deliveries and structured execution scope;
- exact Git broker requests;
- WorkerBee workspace and snapshot policy;
- WorkerBee controlled-run requests, leases, and receipts.

Migration dry-run operates on a copied database. Apply creates a private backup
before changing the live database. Rollback restores the matching database and
optionally the matching configuration. Downgrading the package without
restoring the corresponding older-schema database is not a supported rollback.

## Qualification and activation

Repository qualification uses temporary SQLite databases, disposable tmux
servers, isolated Git repositories, fixture WorkerBee endpoints, and clean
package environments. It does not restart the workstation daemon or TUI,
switch a WorkerBee backend, signal a managed Codex process, or alter a live
runtime mapping.

Before workstation activation:

1. record the exact candidate commit and package hashes;
2. back up the database, configuration, runtime mappings, and package identity;
3. run migration dry-run and integrity verification;
4. restart the daemon without restarting the managed tmux server;
5. launch the TUI through the reviewed local wrapper;
6. verify retained Agents, Operators, forks, panes, Codex sessions, Joplin,
   WorkerBee, model policy, and managed editor state;
7. restore the matching backup and prior package if any check fails.

Running Codex processes do not inherit a newly installed CLI binary. Existing
sessions remain intact until an explicit safe-boundary restart/resume. New
launches and later resumes use the qualified host executable recorded by Agent
PBX.

## Promotion

This candidate is eligible for 2.3.0 only after the exact GitHub/TestPyPI
artifacts pass the release matrix, clean installation, reviewed workstation
activation, and representative Agent/Operator/Joplin/native-terminal smoke.
Stable promotion should change release identity and documentation only. Any
semantic runtime change requires another release candidate.

# Agent PBX 2.3.0rc1

Agent PBX 2.3.0rc1 is the TestPyPI qualification candidate for the v2.3
runtime-policy and resilience release. It extends the v2 control plane with
generation-bound WorkerBee runtimes, governed workspace mobility and snapshot
content, safer model elevation, more reliable managed Joplin operation,
long-running TUI resource controls, and a hardened public browser demo.

This candidate is intended for release-pipeline and activation qualification.
Production users should continue to use Agent PBX 2.2.0 until the same reviewed
changes are published as 2.3.0.

## WorkerBee runtime and workspace governance

Agent PBX now binds each Agent, Operator, edit fork, and review fork to one
verified WorkerBee backend generation and one exact workspace receipt.
Appliance-backed sessions use an Agent PBX policy gateway instead of inheriting
host OSS paths, and a generation change fails closed until the affected session
is rebound.

The control plane keeps OSS, platform-debug, and future user-appliance workspace
domains separate. New policy layers independently govern:

- tool authority, from conservative observation through bounded local deploy;
- workspace mobility through pinned, same-repository, or scoped-workbench
  movement;
- snapshot content through tracked, approved-paths, or safe-working-tree modes;
- backend selection, including loopback versus qualified native-LAN posture;
- administrator ceilings that ordinary clients cannot weaken.

The committed public default remains conservative and approval-gated. Setup
presets make standard OSS, personal appliance, trusted platform workbench, and
high-assurance workflows explicit without silently switching backends or
granting deploy authority. Review forks remain read-only under every preset.

Platform-debug materialization is content-addressed. Repeating an approved
session start can refresh changed source while retaining the Codex thread,
gateway lease, token, and backend generation; any further drift blocks mutation
until another qualified refresh. Dirty submodule content requires a host-owned,
Agent-and-source-bound include policy and contributes to binding identity.

## Runtime and operator reliability

- Managed Agent launch pins Agent identity, project, cwd, PBX mode, model,
  reasoning effort, reasoning summary, verbosity, tmux binary, and runtime
  socket instead of inheriting daemon-launcher values.
- Operator campaign delivery recognizes Codex beneath a validated managed-tmux
  shell wrapper and records whether identity came from the foreground command
  or the bounded process tree.
- Prompt delivery exits tmux copy mode before submission so the input reaches
  Codex.
- Bounded Sol-max elevation is idempotent across the TUI, palette, API retries,
  and concurrent clients. One-task leases remain `revert_pending` until a
  structured safe turn boundary permits verified restart/resume on the prior
  profile.
- Agent PBX identity and bearer-token environment survive restart/resume in an
  existing managed pane.

## Long-running TUI and daemon behavior

The embedded terminal now defaults to a 10 FPS paint ceiling while continuing
to consume every PTY byte. It retains only a small renderer-side history when
tmux owns scrollback, skips redundant capture polling for an attached client,
and exposes event-loop lag, process RSS, PTY throughput, paint rate, and frame
coalescing in `Latest`.

Agent refresh and remote view persistence coalesce repeated work without
canceling in-flight HTTP requests. The TUI uses a bounded keepalive pool and
reduces HTTP polling while the event stream is healthy. Managed daemon logs
rotate during runtime with bounded size and backup counts while preserving the
daemon's open output descriptor.

The active workstation TUI has exercised this runtime baseline for more than
five continuous days, and the daemon has exercised the long-run resource paths
for more than nine days. The exact candidate still receives the standard
post-activation smoke check before stable publication.

## Managed Joplin consistency

- Daemon startup restores the configured Data API listener in `managed_cli`
  mode only after validating the profile owner, PID, executable, command, and
  socket posture.
- Profile sync waits for the listener socket itself to release, closing the
  `EADDRINUSE` race that could follow a clean process exit.
- Status reads durable queued/running state before probing a deliberately
  stopped listener, and the TUI retains known configuration and cached notes
  through a bounded restart.
- Completed `jc` writes render locally without waiting for the next refresh.
- Targeted write jobs remain Agent-scoped and cannot coalesce across owners.
- `/joplin retry write` requeues the selected Agent or Operator's latest failed
  targeted write without duplicating the note or requiring a whole-profile
  E2EE validation pass.

## Public browser demo and release media

The optional public demo now gives its root Operator and both Operator forks
independent native tmux runtimes while retaining Release Review in report mode.
Every visitor still receives isolated state, fixtures, credentials, tmux, and
processes.

The browser waits for authoritative font, iframe, visual-viewport, and Textual
Serve geometry before opening the TUI, then performs a bounded first-frame
resynchronization. An accessible Agent PBX loading surface reports startup
progress, honors reduced-motion preferences, and offers a safe retry when a
disposable session closes early.

An isolated media harness can capture deterministic ultrawide native Latest,
Operator campaign, WorkerBee, and managed Neovim scenes. It verifies frame
markers, forbidden text, geometry, source revision, and asset hashes without
attaching to workstation runtimes.

## Compatibility and migration

Agent PBX 2.3 adds three schema-31/32 tables for WorkerBee workspace policy,
snapshot policy, and workspace transition records. The migration is additive;
existing Agent, Operator, fork, campaign, Codex-session, Joplin, editor, and
managed tmux records remain valid.

An isolated schema-30 fixture proves dry-run, apply to schema 32, retained
starred Agent/root Operator/event data, verification, and rollback to schema
30. The production upgrade still requires the normal database/configuration
backup and a reviewed activation window. Running Codex panes do not need to be
restarted solely for the package update.

Compatibility polling, Thread, HTTP refresh, and captured-terminal paths remain
available. The managed PaaS/user-appliance materializer remains unavailable
until its volume and lifecycle boundary is qualified.

## TestPyPI qualification

The release candidate is accepted only after:

- documentation, wiki, compilation, and diff gates;
- the complete parallel and isolated serial pytest lanes;
- strict release metadata and immutable-tag validation;
- isolated PEP 517 wheel and source-distribution builds;
- strict Twine and archive-hygiene checks;
- clean virtual-environment installation from the exact wheel;
- the hosted Linux/macOS and Python 3.10/3.12 matrix;
- TestPyPI Trusted Publishing, public hash comparison, and clean installation.

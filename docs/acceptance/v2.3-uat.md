## Split-policy linked-Git broker qualification

The follow-on provider-free qualification preserves direct runtime grants for
compatible base profiles and adds a different strategy only where Codex 0.166
cannot compose the four Git-admin writes with split secret/read/deny policy.
The broker is callable only through the local TUI for one explicitly selected,
canonical `canceled`, inactive edit fork. It is not imported by API/MCP/server
routes and rejects direct-compatible or review/read-only forks.

Receipt preparation begins from an empty staged set and observes only an exact
root-provided leaf list. Each leaf binds state, mode, raw SHA-256/blob OID,
prior index mode/OID, no-follow parent-chain identity, and stable file identity.
The confirmation surface also binds branch, HEAD/tree, index, upstream/OID,
ref/reflog, transaction, and TUI authority identities. Raw-byte
`hash-object --no-filters` semantics avoid worktree attributes and external
clean filters. Qualification uses an absolute Git binary, sanitized
environment, replacement-object and lazy-fetch disablement, and rejects local
or worktree include/includeIf, partial-clone/promisor configuration, and object
alternates before repository-aware Git commands.

Linux strace tests execute real child Git processes around candidate review and
receipt preparation. They prove that an unapproved sentinel `.gitattributes`
and protected environment file are never opened, statted, or readlinked, and
that include-bearing config fails before its external target is opened. The
portable unit lane independently rejects protected-path arguments and file
helper access; non-Linux hosts skip only the process-trace assertion.

Approved blobs, tree, and commit are first created in a private `0700` journal
object quarantine. The exact object manifest is fsynced and journaled before
the first shared object installation. The durable journal accepts only an
exact typed schema and known phase, with installed objects forming the
canonical prefix required by that phase. Unknown/extra/mistyped state,
reordered progress, impossible phase/progress, foreign receipts, ambiguous
transactions, and identity drift cause zero recovery mutation even when the
repository happens to match the old ref/index state.

Git's conventional index lock plus dedicated-ref compare-and-swap provides
logical index/ref/reflog atomicity. Recovery either completes the exact new
state, restores the exact old state, or stops for manual review. Standard Git
object creation remains append-only: after a later race/rollback, only the
journaled objects derived from approved bytes/tree/commit may remain
unreachable. They are disclosed for normal Git garbage collection and are
never deleted during rollback.

### Structural Git-index validation

Receipt preparation parses the Git index rather than searching its complete
byte stream for extension names. The parser validates the `DIRC` header,
supported v2-v4 entry layouts, repository object-ID width, declared entry count,
pathname terminators and v4 prefix compression, v2/v3 padding, extension
headers and payload sizes, and the trailing SHA-1/SHA-256 checksum. Only
signatures in the structurally located extension table affect policy.

Fixtures prove that ordinary pathname bytes containing `link` or `sdir`, a safe
`TREE` extension, real Git index v4, and SHA-256-width entries are accepted.
Actual `link`/`sdir` extensions remain denied. Truncated entries, invalid flags,
non-NUL padding, malformed signatures, duplicate or unknown mandatory
extensions, impossible counts, extension overflow, unsupported versions/object
formats, invalid v4 removal counts, and checksum drift all fail closed. A real
split-index fixture is rejected, while the tracked-path marker regression now
produces an immutable preparation receipt without creating a journal.

## Inactive missing-runtime reconciliation qualification

The follow-on TUI repair is source-only and provider-free. A canceled,
PBX-inactive edit fork's `missing` durable mapping is evicted from the local TUI
cache only when all of the following evidence agrees:

- a fresh authenticated runtime lookup probed the mapping's exact tmux socket;
- mapping socket and server ID are self-consistent and match the Agent's
  recorded runtime server ID/mode;
- mapping session, pane, and Codex session match the Agent's authoritative
  fork metadata;
- no writer client or lease, live pane, embedded client, or terminal transition
  remains, with pane absence proved by a fresh local/outer tmux listing; and
- the recorded PID/start-time identity is conclusively absent. An unreadable or
  malformed proc record remains ambiguous and blocks cleanup.

The TUI compares bare pane collisions only after qualifying their server
provenance. Therefore an unrelated outer-server `%12` cannot preserve a
missing dedicated-runtime `%12`, while same-server, missing-server,
missing-socket, mismatched-session, active-writer, live-process, `ready`, and
`starting` cases all fail closed. Repeated fetch and refresh paths do not
re-cache the qualified missing record, and unrelated mapping entries remain
unchanged.

The synchronous broker guard never invents pane-absence evidence from its local
cache. A normal TUI refresh obtains the fresh pane list and performs the
target-local reconciliation first; an unavailable pane query or a matching
outer pane leaves the mapping in place and the broker unavailable.

# Codex subagent activity qualification

Last reviewed: 2026-10-10

Agent PBX exposes Codex child activity only after a structured event from the
Codex thread already bound to the owning Agent or Operator. The child remains a
read-only runtime projection beneath that PBX identity. It does not become a
PBX peer, campaign assignee, command recipient, or independent policy subject.

The v2.1.2 fixtures cover both protocol forms observed during the v2 cycle:

| Codex protocol form | Qualification |
|---|---|
| `collabAgentToolCall` | Spawn/collaboration receiver IDs and lifecycle status normalize into generic child records. Prompt, reasoning, and status messages are discarded. |
| `subAgentActivity` | Current activity kinds (`started`, `interacted`, `interrupted`, and `completed`) normalize into bounded child lifecycle records. `agentPath` is discarded and never treated as proof of a named role. |

The local Codex CLI `0.162.0` generated an app-server schema with both forms,
the required child identifiers, and the four current activity kinds. The probe
observed the app-server schema and advertised multi-agent support without
starting a Codex turn or child.

Acceptance coverage proves that:

- unrelated thread IDs cannot update the projection;
- the child record always names its owning PBX parent;
- a role stays unset unless a future trusted protocol field proves it;
- current, compatibility, unknown, and partial lifecycle events do not crash;
- child paths, prompts, hidden reasoning, and status messages never enter the
  normalized snapshot or PBX event journal;
- the TUI hides the tree until native subagent capability is observed;
- Operator and review-fork instructions require every child to inherit the
  owning session's workspace and tool restrictions.

Live child spawning remains an operator-controlled UAT because it starts model
work. The protocol/schema probe and deterministic projection tests are safe to
run in the default suite.

# Agent PBX v2.4.0 acceptance record

This record covers the durable engineering control-plane and Operator workflow
projection delta after Agent PBX v2.3.0. Repository qualification remains
separate from live workstation activation: it uses temporary state, copied
SQLite fixtures, disposable tmux servers, isolated Git repositories, fixture
WorkerBee endpoints, and clean package environments.

## RC1 hosted-matrix finding and RC2 repair

The immutable `v2.4.0rc1` tag passed validation, distribution construction,
Ubuntu/Python 3.10, and the local workstation activation boundary. Its
Ubuntu/Python 3.12 lane deterministically rejected the Python interpreter
already executing Agent PBX because the hosted tool-cache installs that
interpreter with a group-writable mode. Six durable-helper tests failed before
helper syntax validation. RC1 was therefore not published to TestPyPI or
created as a GitHub prerelease.

RC2 permits the resolved current-process interpreter under that distribution
mode while retaining the no-group-or-world-write rule for every separately
configured validator. Exact path resolution, regular-file and owner-execute
checks, isolated non-executing compilation, private harness directories, and
before/after executable identity checks remain unchanged.

## Activation contract

Activation is allowed only after the immutable RC identity and local package
artifacts are qualified. The activation sequence must:

1. record installed package, daemon, TUI, schema, database, configuration, and
   runtime-mapping identity;
2. make a timestamped database/configuration backup and verify it;
3. run migration dry-run against a copy;
4. install the qualified local RC artifact;
5. restart the daemon without restarting the managed tmux server;
6. launch the TUI through `apbx local`;
7. verify retained Agents, Operators, forks, stars, campaigns, panes, Codex
   session IDs, Joplin, WorkerBee, model policy, and managed editor state; and
8. retain the rollback package and backup until reviewed UAT completes.

Feature gates remain at their reviewed local values. The RC activation does
not automatically enable a private WorkerBee adapter, provider authority,
network/device/credential resources, publication, deployment, or destructive
actions.

## Rollback

If activation fails, stop new work, disable affected feature gates, release
only exact receipt-bound resources, preserve immutable evidence, stop the RC
daemon without killing managed tmux/Codex runtimes, restore the prior package
and matching database/configuration backup, restart the daemon, and verify the
same retained identity matrix. Never infer cleanup targets or delete shared
Git, WorkerBee, provider, helper, KB, or runtime objects.
